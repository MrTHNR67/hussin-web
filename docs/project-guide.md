# سياج (Siyaj) — دليل المشروع الشامل

> رفيق الطاقة الشمسية: تطبيق عربي يحسب فقدان إنتاج الألواح ويقدّر قيمته المالية، ويذكّر بالصيانة، دون حساب أو كلمة مرور.
>
> النسخة الحية: **https://siyaj-web.onrender.com** · الكود: **https://github.com/MrTHNR67/hussin-web**

## 1. فكرة الموقع ورحلة المستخدم من البداية للنهاية

### الفكرة
أصحاب الأنظمة الشمسية غالباً لا يكتشفون فقدان الإنتاج إلا عند ارتفاع الفاتورة. المشكلة تظهر بصمت بسبب الحرارة أو الغبار أو سوء التوجيه أو اقتراب موعد الصيانة. «سياج» يحوّل هذه العوامل إلى أرقام مفهومة:

- كمّ الطاقة التي نفقدها؟ (نسبة مئوية وكيلوواط/ساعة)
- كم تساوي الخسارة بالريال العماني؟
- متى موعد الصيانة القادمة؟
- ما التوصية العملية الآن؟

### الرحلة الكاملة

| الخطوة | ما يحدث | أين يحدث |
|---|---|---|
| 1. الدخول | يُفتح الرابط مباشرة. شاشة الدخول القديمة أُزيلت؛ يظهر حقلان فقط: **الاسم** و**القبيلة**. أي اسم يبدأ التجربة، بلا كلمة مرور أو تسجيل. | `public/index.html` → `#page-auth` |
| 2. حفظ الهوية | يُحفظ الاسم والقبيلة ورمز الجلسة في متصفح الزائر، وتُنشأ جلسة على الخادم عبر ملف ارتباط `HttpOnly`. | `public/app.js` + `/api/auth/guest` |
| 3. المعالج — خطوة 1: البيئة والموقع | إمكانية استخدام GPS أو البحث عن مدينة، ثم حرارة الجو والرطوبة وعدد الألواح ومؤشر الغبار. يُجلب الطقس تلقائياً بعد تحديد الموقع. | `renderCurrentStep()` |
| 4. المعالج — خطوة 2: الألواح | القدرة الإجمالية، الشركة المصنّعة، تاريخ آخر صيانة، ميل اللوح، اتجاه الواجهة، وقت التصوير، نوع اللوح، الكفاءة ومعامل الحرارة، مع إمكانية إرفاق صور/فيديو. | نفس الدالة + `/api/geocode`, `/api/weather` |
| 5. المعالج — خطوة 3: الفاتورة | قيمة الفاتورة، الاستهلاك، التعرفة، شهر الفاتورة، الإنتاج المتوقع والفعلي، وصورة الفاتورة اختيارياً. | نفس الدالة |
| 6. المعالج — خطوة 4: التأكيد | مراجعة كل البيانات قبل اعتمادها وحساب النتيجة. | `state.form` |
| 7. لوحة النتائج | بطاقة الحالة، مؤشرات الخسارة (حرارة/غبار/ظل)، توصية سياج، دورة الصيانة كل 6 أشهر، «قراءة تقديرية للألواح» (~2.5 ثانية داخل المتصفح)، خسارة الشهر بالريال، مخطط الأسبوع، وملخص النظام. | `#page-dashboard` |
| 8. بقية الصفحات | السجل، البلاغات والشكاوى، تقرير النظام، الإعدادات (اللغة، الوضع الليلي، الإشعارات، تصدير البيانات). | `#page-history`, `#page-complaints`, `#page-system`, `#page-settings` |
| 9. العودة لاحقاً | فتح الرابط في نفس المتصفح يستعيد الاسم والجلسة ويعود إلى لوحة النتائج دون إعادة إدخال. | `localStorage` + `/api/auth/session` |

الانتقال بين الصفحات يستخدم حركة **squash & stretch**، والأزرار تستخدم **slow in / slow out**، والأيقونات تكبر عند التحويم، مع احترام إعداد «تقليل الحركة» في النظام.

## 2. التقنيات ولغات البرمجة المستخدمة

| التقنية | الغرض في المشروع |
|---|---|
| **HTML5 + CSS3** | بناء الصفحات الخمس والتصميم المتجاوب والوضع الليلي وقواعد الطباعة. بلا مكتبات واجهة. |
| **JavaScript (ES Modules)** | كل منطق الواجهة: المعالج، الحسابات المحلية، الحركة، التخزين، واستدعاءات API. |
| **Node.js 20+** | بيئة التشغيل؛ المشروع مضبوط كـ `type: module`. |
| **Express 4** | خادم HTTP وتقديم الملفات الثابتة ومسارات REST. |
| **PostgreSQL 16** | قاعدة بيانات الإنتاج على Render، عبر مكتبة `pg`. |
| **sql.js (SQLite في WASM)** | قاعدة بيانات محلية للتشغيل والتطوير والاختبارات بدون خدمة خارجية. |
| **Open-Meteo** | الطقس الحالي، جودة الهواء/الغبار، الأرشيف التاريخي، وتحديد أسماء المدن (Geocoding). |
| **MET Norway** | مصدر بديل تلقائي للطقس عند تعذّر Open-Meteo. |
| **Anthropic Claude** | قراءة فاتورة الكهرباء (OCR) اختيارياً، مخفي خلف مفتاح API ومفتاحه غير مفعّل افتراضياً. |
| **Web Push (web-push / VAPID)** | تنبيهات الغبار والرياح والصيانة على الهاتف. |
| **Nodemailer** | إرسال البلاغات والشكاوى عبر البريد عند تهيئة SMTP. |
| **google-auth-library** | مسار قديم لتسجيل الدخول عبر Google ما زال موجوداً في الخادم فقط، ولا يظهر في الواجهة. |
| **Render + Cloudflare edge** | الاستضافة، HTTPS، والـ CDN. المنطقة: Frankfurt. |
| **PWA** | `manifest.webmanifest` + `service worker` لتثبيت الموقع على الشاشة الرئيسية. |
| **node:test** | 15 اختباراً آلياً للجلسات والحركة وسلوك الذروة/النهاية. |

أوامر التشغيل: `npm start` للتشغيل، و`npm test` للاختبارات.

## 3. شرح Frontend وBackend وقاعدة البيانات

### أ) Frontend — `public/`

| الملف | المسؤولية |
|---|---|
| `index.html` | الصفحة الرئيسية وكل البطاقات والمعالج. |
| `app.js` | حالة التطبيق (`state`)، عرض الصفحات، المعالج، الحسابات، رفع الوسائط، وحفظ الهوية. |
| `styles.css` | التصميم، الألوان، التجاوب مع الهاتف، والوضع الليلي. |
| `motion.css` / `motion.js` | منحنيات الحركة المعتمدة، حركة انتقال الصفحات، وتجاهل الحركة عند `prefers-reduced-motion`. |
| `about.html` / `privacy.html` | صفحة المشروع وسياسة الخصوصية المحدّثة لوضع الزائر. |
| `sw.js` / `manifest.webmanifest` | دعم التثبيت والتخزين المؤقت الأساسي. |

لا يوجد إطار عمل (React/Angular/Vue)؛ الواجهة مكتوبة بـ JavaScript صريح لتقليل الحجم وتبسيط النشر على الخطة المجانية.

### ب) Backend — `server.mjs` + مجلد `server/`

خادم Express واحد يقدّم الواجهة ويدير API:

| المجموعة | المسارات | الوظيفة |
|---|---|---|
| الصحة | `/healthz`, `/readyz` | فحص الحياة وجاهزية قاعدة البيانات. |
| التهيئة | `/api/config`, `/api/app-settings`, `/api/push/config` | إعدادات الحدود والمناخ والتنبيهات. |
| الجلسات | `/api/auth/guest`, `/api/auth/session`, `/api/auth/logout` | دخول الزائر بالاسم والقبيلة واستعادة الجلسة. مسارات `signup/login/google` ما زالت في الخادم لأغراض توافقية فقط ولا تظهر في الواجهة. |
| الحساب | `/api/account/state`, `/api/account/media` | حفظ/قراءة حالة المستخدم وصوره (25MB للملف). |
| الألواح والتحليل | `/api/panel/sync`, `/api/panel/cleaned`, `/api/panel/analysis`, `/api/panel/delete`, `/api/monthly-loss`, `/api/analyze` | مزامنة بيانات النظام، حساب الخسارة الحرارية والغبار، وتحليل فاتورة اختياري. |
| الطقس والموقع | `/api/weather`, `/api/geocode` | وكيل آمن لخدمات الطقس وتحديد المدن. |
| التنبيهات والبلاغات | `/api/jobs/daily-alerts`, `/api/push/*`, `/api/complaints` | جدولة فحص الغبار/الرياح، الاشتراك بالإشعارات، وإرسال الشكاوى. |
| الإدارة | `/api/admin/stats`, `/api/auth/events` | إحصاءات وسجل أحداث محمية بدور `admin` فقط. |

وحدات مساندة: `auth.mjs` (الجلسات والأدوار)، `data-store.mjs` (قاعدة البيانات والوسائط)، `weather-data.mjs` (الطقس والبديل)، `solar-assessment.mjs` (زاوية الشمس والخسارة الشهرية)، `heat-loss-report.mjs`، `security.mjs` (الرؤوس)، `rate-limit.mjs` و`audit.mjs`.

### ج) قاعدة البيانات

**الإنتاج (PostgreSQL على Render):**

| الجدول | المحتوى |
|---|---|
| `public.siyaj_app_state` | صف واحد (`id=1`) يحفظ حالة التطبيق كـ `JSONB` مع وقت التحديث. |
| `public.app_settings` | إعدادات المناخ/الحدود كمفتاح → `JSONB`. |
| `public.panel_analyses` | سجلات التحليل مع نسب وقيم خسارة الغبار والحرارة والسجل الكامل `record_json`. |
| الجداول المحلية المقابلة (SQLite) | `users`, `auth_sessions`, `auth_events`, `account_states`, `account_media`, `panel_data`, `push_subscriptions`, `panel_analyses`, `ai_usage`. |

تفاصيل مهمة:
- الاتصال عبر `DATABASE_URL` من متغيرات بيئة Render فقط، مع SSL مُدار. لا توجد كلمة سر أو رابط قاعدة داخل Git.
- تفعيل **RLS** على الجداول المشتركة وسحب صلاحيات `PUBLIC` و`anon` و`authenticated` منها.
- الجلسات تُخزّن كـ **hash للرمز** لا كرمز صريح، مع تاريخ إنشاء وآخر ظهور.
- عند غياب `DATABASE_URL` يعمل التطبيق محلياً بـ SQLite، وهذا ما تستخدمه الاختبارات.

## 4. إمكانية الربط مع منصات الطاقة الشمسية

### الوضع الحالي
لا يوجد حتى الآن ربط مباشر بالعواكس أو منصات المراقبة (مثل SolarEdge أو Enphase أو Huawei FusionSolar أو SMA أو Fronius). ما يوجد اليوم:

- ربط خارجي بالطقس فقط (Open-Meteo + MET Norway) عبر الخادم.
- إدخال **الإنتاج المتوقع والفعلي** يدوياً من قراءة العدّاد أو تطبيق المنصة (`expectedMonthlyKwh` / `actualMonthlyKwh`).
- مسارات داخلية قابلة لأن تكون نقطة دخول للربط: `/api/panel/sync` و`/api/panel/analysis`.
- مخطط قاعدة يحفظ `panel_data` و`panel_analyses` و`account_states`.
- جدولة يومية `/api/jobs/daily-alerts` يمكن توسيعها لسحب بيانات الإنتاج.

### كيف يتم الربط لاحقاً (المقترح العملي)
1. إنشاء طبقة `server/integrations/` بواجهة موحّدة: `fetchGeneration(credentials, from, to)`.
2. تنفيذ محوّل (adapter) لكل منصة: OAuth أو API key، مع احترام حدود الطلبات وإعادة المحاولة.
3. خدمة مزامنة مجدولة تكتب النتائج في `panel_data` و`panel_analyses` وتحدّث `actualMonthlyKwh`.
4. ربط التنبيهات: أي هبوط غير مبرر في الإنتاج يُقارن بالطقس والغبار قبل إرسال إشعار.
5. واجهة في الإعدادات لاختيار المنصة ومنح الموافقة، مع تخزين الأسرار في متغيرات البيئة أو مخزن أسرار، لا في المتصفح.
6. بيئة اختبار (sandbox) لكل منصة قبل تفعيلها للعملاء.

| ميل اللوح واتجاه الواجهة ووقت التصوير | اختياري (يُتحقق من النطاق عند الإدخال) | حساب زاوية سقوط الشمس والظل. |

| شهر الفاتورة | نعم في خطوة الفاتورة | تحديد الفترة التي تُقَيَّم. |
| قيمة الفاتورة | اختياري، ويصبح مطلوباً عند إدخال الاستهلاك | حساب قيمة الطاقة المفقودة بالريال. |
| الاستهلاك، التعرفة، الإنتاج المتوقع/الفعلي | اختيارية | تحسين دقة التقدير والمقارنة الشهرية. |

## 6. آلية حماية بيانات العملاء

| الإجراء | التنفيذ في المشروع |
|---|---|
| جلسات آمنة | ملف ارتباط `HttpOnly` + `SameSite` هو الأساس؛ ورمز حامل (Bearer) احتياطي يُحفظ في `localStorage` لاستعادة الجلسة في نفس المتصفح. |
| فصل الصلاحيات | دور `guest` للمستخدم العادي؛ مسارات `admin` تُرجع `401` بدون جلسة و`403` لزائر عادي (تم التحقق منها على الموقع الحي). |
| تخزين الرموز | الجلسات تُحفظ كـ `hash` في قاعدة البيانات، لا كنص صريح. |
| عزل الجداول | RLS مفعل على الجداول المشتركة، وسحبت صلاحيات `PUBLIC`/`anon`/`authenticated`. |
| رؤوس أمنية | CSP صارم، HSTS في الإنتاج، منع `X-Powered-By`، وضبط `trust proxy`. |
| حماية من التخمين | حد 30 طلباً/دقيقة لمسارات المصادقة و20 لتسجيل الدخول، مع قفل مؤقت بعد 10 محاولات فاشلة لمدة 15 دقيقة، وسجل أحداث مصادقة. |
| التحقق من المدخلات | حدود طول ونطاقات رقمية ونوع ملف و25MB كحد للمرفقات و18MB لجسم JSON. |
| الأسرار | `DATABASE_URL` والمفاتيح في متغيرات بيئة Render فقط؛ `.env` مستبعد من Git، ولا يظهر أي سر في المستندات أو المحادثة. |
| الخصوصية افتراضياً | صور الألواح تبقى في المتصفح؛ إرسال الفاتورة إلى Claude لا يحدث إلا بضغط الزر وبوجود مفتاح مُهيّأ. صفحة `privacy.html` تشرح ذلك. |
| التدقيق | أحداث الدخول والخروج والمحاولات الفاشلة تُسجّل في `auth_events`. |

**ما زال يحتاج تحسيناً:** لا يوجد MFA ولا WAF بعد، وتحديد المعدل لكل نسخة خادم لا لكل مستخدم، ورمز `localStorage` يحمل خطر XSS متبقياً (مطلوب لاستعادة الجلسة في نفس المتصفح).

## 7. تجهيز نسخة تجريبية Demo للموقع

**الرابط:** https://siyaj-web.onrender.com

خطوات التجربة (أقل من دقيقتين):

1. افتح الرابط (الضغط الأول قد يستغرق 30–50 ثانية بسبب نوم الخطة المجانية).
2. أدخل أي اسم وأي قبيلة → اضغط «ابدأ التجربة».
3. أكمل المعالج: الموقع أو GPS → البيانات البيئية → بيانات الألواح → الفاتورة → التأكيد.
4. في لوحة النتائج جرّب:
   - زر «قراءة تقديرية للألواح»: شريط تقدّم ~2.5 ثانية ثم رسالة «تم تجهيز القراءة التقديرية»، بدون أي طلب للخادم.
   - تغيير اللغة/الوضع الليلي من الإعدادات.
   - صفحات السجل والبلاغات وتقرير النظام.
5. أعد تحميل الصفحة: يبقى الاسم والقبيلة والجلسة.

فحوص جاهزة للحكّام:

```powershell
curl.exe -s -o NUL -w "root    %{http_code}`n" https://siyaj-web.onrender.com/
curl.exe -s -o NUL -w "healthz %{http_code}`n" https://siyaj-web.onrender.com/healthz
curl.exe -s -o NUL -w "readyz  %{http_code}`n" https://siyaj-web.onrender.com/readyz
curl.exe -s -o NUL -w "admin   %{http_code}`n" https://siyaj-web.onrender.com/api/admin/stats
```

المتوقع: `200 / 200 / 200 / 401`.

## 8. المشاكل التقنية الحالية والحلول المقترحة

| المشكلة | الأثر | الحل المقترح |
|---|---|---|
| الخطة المجانية تنام بعد ~15 دقيقة خمول | أول طلب يستغرق 30–50 ثانية | ترقية الخطة أو إضافة خدمة إحماء (ping) مجدولة؛ وتُعرض رسالة تحميل واضحة للمستخدم. |
| قاعدة Postgres المجانية تنتهي في **2026-12-11** | توقف حفظ البيانات عند الانتهاء | تصدير البيانات من الإعدادات قبل الموعد، ثم ترقية قاعدة Render أو نقلها إلى Postgres مُدار دائم. |
| المرفقات تُحفظ على قرص النسخة | تُفقد عند إعادة النشر | تفعيل `SUPABASE_URL` + `SUPABASE_SECRET_KEY` + bucket خاص (الخادم يدعم ذلك بالفعل). |
| قراءة الألواح محاكاة بصرية 2.5 ثانية | ليست ذكاءً اصطناعياً حقيقياً | ربط نموذج vision حقيقي عبر `/api/analyze` مع قياس الثقة وعرض تحذير «تقديري». |
| لا ربط بالعواكس | الإنتاج يُدخل يدوياً | طبقة adapters كما في القسم 4. |
| رمز الجلسة في `localStorage` | خطر XSS متبقٍ | نقل الرمز إلى `HttpOnly` فقط بعد Adding `SameSite=Strict` ومراجعة CSP، أو استخدام سessions server-side كاملة. |
| تحديد المعدل لكل نسخة | لا حماية موزّعة | Redis مشترك أو تقييد على مستوى الحافة (Cloudflare Rate Limiting). |
| لا MFA ولا WAF | حماية إدارية محدودة | تفعيل MFA للحسابات الإدارية وقواعد WAF على الحافة. |
| مسارات `signup/login/google` ما زالت في الخادم | سطح هجوم غير مستخدم | حذفها نهائياً بعد التأكد من عدم استخدامها، والاكتفاء بمسار الزائر. |
| منطقة واحدة (Frankfurt) | لا مرونة إقليمية | نسخة ثانية في منطقة أخرى مع DNS failover عند توفر الميزانية. |

## 9. خطة تطوير الموقع مستقبلًا

### المرحلة 0 — الاستقرار والتسليم (الحالية)
- ✅ نشر على Render، دخول بالاسم والقبيلة، كل الصفحات محفوظة.
- ✅ اختبارات آلية 15/15 وتوثيق كامل.
- ✅ رفع الخريطة البصرية لزاوية اللوح حسب طلب المستخدم.
- □ استكمال بيانات الفريق في نموذج التسليم.

### المرحلة 1 — متانة التشغيل (1–2 شهر)
- تخزين المرفقات في object storage خاص.
- جدولة حقيقية للتنبيهات بدل الاعتماد على مؤقت الخادم.
- مراقبة وقياسات (latency, errors, cost) ولوحات تشغيل.
- MFA للحسابات الإدارية + WAF على الحافة.

### المرحلة 2 — ذكاء وربط (2–4 أشهر)
- ربط العواكس والمنصات (SolarEdge/Enphase/Huawei/SMA) عبر adapters.
- قراءة فاتورة حقيقية وقراءة صور الألواح بنموذج vision مع نسبة ثقة.
- مقارنة الإنتاج الفعلي بالمتوقع آلياً وكشف الانحراف.

### المرحلة 3 — تجربة المستخدم (4–8 أشهر)
- تطبيق PWA كامل يعمل دون اتصال للقراءة فقط.
- تقارير PDF قابلة للمشاركة مع الفني أو المورّد.
- دعم أكثر من نظام لكل عميل، وصلاحيات فرق الصيانة.

### المرحلة 4 — التوسّع (بعد 8 أشهر)
- مناطق نشر متعددة ومرونة إقليمية.
- واجهة API شريكية للمورّدين والفنيين.
- دعم لغات إضافية وتوسّع جغرافي.

**مؤشرات النجاح المقترحة:** تقليل زمن اكتشاف فقدان الإنتاج، نسبة المستخدمين الذين ينفّذون التوصية، دقة تقدير الخسارة مقابل قراءة العدّاد، وتوفر الخدمة ≥ 99%.
